**다음 작업은 입력·게시 무결성 보완과 실행 버전 정렬을 먼저 하는 것이 좋습니다.** 그다음 실제 갱신되는 공개 원천 하나를 연결하면 산업 데이터 엔지니어링과 포트폴리오 양쪽에서 가치가 큽니다. Kubernetes는 현재의 작업 격리·재시도 시연 범위를 유지하고, 병렬화는 처리시간 목표가 생겼을 때 확대하는 편이 타당합니다.

기준 커밋 `4bb9051`의 핵심 코드를 직접 확인했습니다. 원본 캡처 후 처리, 일별 트랜잭션 게시, 단일 SELECT 보고서 스냅샷, 조직 필터, 추정 에너지와 검토 후보의 구분은 구현되어 있습니다. 다만 다음 경계는 보완할 필요가 있습니다.

확인한 결함과 위험은 다음과 같습니다.

1. **인버터 ID 표현이 섞이면 품질 분모가 잘못됩니다 — 메모리 재현으로 확인.**
   [source_bounds](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/src/solarops/pipeline.py#L51)는 문자열 `inverter_id`로 집계한 뒤 `int()`를 키로 사용합니다. 반면 [정규화](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/src/solarops/normalize/parquet.py#L63)는 처음부터 정수로 변환합니다. 서로 다른 시각의 `01`과 `1`은 같은 인버터로 처리되지만, 기대 범위는 한쪽으로 덮어써집니다. 두 관측을 넣은 메모리 검사에서 **관측 2, 기대 1, 유효 관측률 200%**를 확인했습니다. 기존 공개 자료에 이 사례가 있다는 증거는 없지만, 현재 입력 검사가 허용하는 계산 결함입니다.

2. **압축 해제 중단이 정식 경로에 불완전 CSV를 남깁니다 — 가상 파일시스템 재현으로 확인.**
   [safe_extract](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/src/solarops/acquisition/brpvgen.py#L119)는 최종 파일을 직접 열어 복사합니다. 헤더와 첫 행 이후 실패시키자 최종 이름의 파일이 남았고, 재실행은 `Existing extracted data differs`로 중단됐습니다. 이후 처리기는 [현재 파일의 SHA](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/src/solarops/pipeline.py#L119)를 계산할 뿐 ZIP 멤버의 완전성과 연결하지 않습니다. 따라서 행 경계에서 잘린 CSV는 짧아진 정상 관측 범위처럼 처리될 위험이 있습니다. 실제 저장소에서 이 후속 적재까지 실행하지는 않았습니다.

3. **게시 경계가 발전소 메타데이터와 동시 버전 실행을 충분히 보호하지 않습니다.**
   [발전소 metadata 갱신](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/src/solarops/pipeline.py#L160)은 일별 검증 전에 커밋됩니다. 실제 `ingest`를 메모리 DB에서 실행하고 뒤의 검증을 실패시키자, **실행은 failed·활성 결과 용량은 20kW인데 발전소 목록용 용량은 30kW**가 됐습니다. [목록 API](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/src/solarops/api/app.py#L113)는 변경된 dimension을 읽습니다. 기존 결과 보존 원칙과 조회 일관성이 어긋나는 결함입니다.
   또한 [일별 active 갱신](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/src/solarops/pipeline.py#L363)은 잠금 이후 무조건 덮어씁니다. 실제 `publish_day`의 완료 순서를 메모리에서 `v2 → v1`로 만들자 최종 active는 `v1`이었습니다. 잠금은 커밋 충돌을 직렬화하지만 오래된 실행의 덮어쓰기를 막지 않습니다. 버전 이름에 순서 계약이 없으므로, **최신 버전 정책을 정하고 강제해야 할 위험**입니다. 현재 공개 결과가 이미 되돌아갔다고 확인한 것은 아닙니다.

4. **같은 공통 CLI를 쓰지만 실행 코드 버전은 다릅니다 — 설정과 Docker 조회로 확인.**
   [Compose](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/infra/compose/compose.yaml#L49)의 worker와 dashboard, [KPO](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/dags/solarops_factory.py#L23)가 서로 다른 이미지 경로를 사용합니다. 조회한 worker 이미지 ID도 기존 `d094ef…`와 최신 dashboard `931878…`로 달랐습니다. Airflow는 중지 상태였으므로 즉시 발생 중인 장애는 아니지만, 재개하면 보고서 선택 범위 등 최신 계약이 실행 경로마다 달라질 수 있습니다.
   앱 의존성은 잠겨 있지만 [Airflow 설치](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/infra/docker/Dockerfile#L16)는 전이 의존성 전체를 고정하지 않습니다. 이미지 기록과 재빌드 재현성은 별개의 문제입니다.

권장 개선안은 여섯 가지입니다. 요소 순서는 **영향/확인 가치/확신/후속 해소/범위 보완/비용**이며, 각 0–3점으로 요청한 산식을 적용했습니다.

각 작업의 최소 범위와 완료 증거는 다음 정도면 충분합니다.

1. **입력 무결성:** 인버터 ID를 범위 계산과 정규화에서 동일하게 해석하거나 비정규 표현을 명시적으로 거부합니다. 압축 해제는 임시 파일에서 끝까지 검증한 뒤 최종 경로로 전환합니다. 완료 증거는 `01/1` 사례의 올바른 분모 또는 명확한 거부, 추출 중단 후 최종 파일 비노출, 재시도 성공입니다. 기존 계약 테스트를 보강하면 충분합니다.

2. **게시 무결성:** 발전소 메타데이터를 게시된 버전과 연결해 실패한 입력이 조회 상태를 바꾸지 않도록 합니다. active 교체에는 기대한 이전 `run_id`를 확인하는 조건부 갱신이나 명시적인 게시 순번을 사용합니다. 의도적인 과거 버전 복원은 별도 동작으로 구분합니다. 완료 증거는 실패 전후 목록·활성 결과 일치, 역순 완료·중복 재시도·겹치는 날짜 실행에서 정해진 결과 유지입니다. 이 부분은 SQLite와 실제 PostgreSQL 양쪽 검사가 필요합니다.

3. **릴리스 정렬:** 커밋·앱/계산 버전·worker/Airflow 이미지 식별자를 하나의 릴리스 명세로 연결하고 Compose·Helm·KPO가 이를 참조하게 합니다. Airflow 의존성도 재현 가능한 제약으로 고정합니다. 완료 증거는 같은 작은 입력의 CLI·Compose·KPO 논리 해시 일치와 보고서 계약 일치입니다. 전체 공개 자료 재처리는 필요하지 않습니다.

4. **증분 수집:** [현재 하드코딩된 출처](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/src/solarops/pipeline.py#L127)를 출처 ID·라이선스·단위·간격·시간대·adapter 버전 계약으로 분리합니다. 실제 갱신 원천 하나에만 성공 수집 위치, 중복·지연·수정 자료 처리, 일별 게시 의존성을 구현합니다. 완료 증거는 같은 응답 재수집의 일관성, 수정 자료의 해당 날짜만 갱신, 실패 시 성공 위치 보존입니다. 원천이 정해지기 전에는 범용 connector 체계를 만들지 않습니다.

5. **관측과 복구:** 이미 있는 [inspect-runs](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/src/solarops/diagnostics.py#L12)에 Airflow 실행·태스크 시도·Pod UID·릴리스 ID를 연결하고 처리 단계·행 수·오류 코드를 구조화합니다. 완료 증거는 중단된 작업 하나를 원인부터 활성 결과, 재시도 결과까지 추적할 수 있는 것입니다. 경과시간만으로 자동 실패 처리하지 않는 현재 원칙은 유지하는 것이 좋습니다.

6. **병렬 처리:** 발전소 또는 충분히 큰 날짜 묶음을 대상으로 동시 2개부터 제한적으로 비교합니다. 현재 [DAG](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/dags/solarops_factory.py#L103)는 단일 발전소·기간 태스크이며, 기존 1/2/4 Pod 기록은 별도 Indexed Job의 작은 합성 시험입니다. 완료 증거는 대표 공개 표본에서 직렬 대비 총시간·CPU·메모리·DB/S3 부하·결과 해시 비교입니다. DuckDB 기본 임시 경로가 `.tmp`인 것도 확인했으므로, KPO의 읽기 전용 루트에서 외부 정렬이 발생하기 전에 쓰기 가능한 spill 경로를 지정해야 합니다. 실제 Pod에서 spill 실패를 재현한 것은 아닙니다.

**실행 순서는 1 → 2 → 3을 권합니다.** 이후 원천과 이용 조건이 정해지면 4를 진행합니다. 원천 선정이 지연되면 독립적으로 수행 가능한 5를 먼저 할 수 있습니다. 6은 처리시간 목표가 없거나 직렬 실행이 충분하면 보류해도 됩니다.

지금 보류할 항목은 다음과 같습니다.

- **Kubernetes 노드 확대·오토스케일링·RWX 도입:** 단일 노드 kind와 공유 PVC의 현재 검증만으로 필요성을 입증하지 못했습니다.
- **Kafka·Spark·lakehouse 도입:** 기존 기록상 1,440만 행의 전체 v2 처리는 약 860초입니다. 우선 해결할 문제가 입력·게시 계약에 있습니다.
- **추가 캐시·광범위한 DB 정규화:** [최근 측정](https://github.com/TaeyanG4/solarops-audit/blob/4bb9051/docs/benchmarks/technical-20261023.md#L31)의 동시 4개 목표는 달성했습니다. 동시 8개 p95 약 2초만으로 추가 구조 변경을 정당화하기 어렵습니다.
- **대형 관측 스택·반복적인 같은 호스트 복원 시험:** 먼저 실행 추적과 복구 계약을 명확히 합니다. 다른 호스트 복원은 필요한 운영 범위와 RTO/RPO가 정해졌을 때 별도 검증합니다.
- **고객 연동·영업·외부 배포:** 요청한 후순위와 현재 범위를 유지합니다.
