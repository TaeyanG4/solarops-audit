## 구체적 발견과 최소 개선

### D1 — 보간 여부 불명인 관측이 보고서에서 0%로 표시됨

- 심각도: **중간(P2)**. 재현 상태: **격리 합성 입력으로 직접 재현**.
- 위치: `src/solarops/analytics/metrics.py:49`, `src/solarops/reports/render.py:72`, `src/solarops/reports/templates/monthly.html:22`, `:25`, `:27`. 화면 보고서의 동일 설명은 `src/solarops/api/static/dashboard.js:1163`에도 있다.
- 최소 입력: 4월 1·2일 각 1개 유효 1000W 관측, 보간 플래그 빈 문자열, sample count 3. 정규화는 보간을 None으로 보존한다. 결과는 observed=2, interpolation_unknown_slots=2인데 report.interpolation=0.0, HTML에는 `원본 보간 표시 … 0.00%`가 나온다.
- 영향: raw·unknown count 자체가 유실되거나 저출력 후보를 생성하는 결함은 아니다. 그러나 독립 HTML의 요약·일별 표에서 '불명'과 '명시적으로 미보간'을 구별할 수 없고, 페이지 설명과 충돌한다. 이번 v0.5.2의 무관측(null) 수정만으로는 이 경우를 해결하지 못한다.
- 최소 개선: 표시된 True 비중을 '확인된 보간 표시 비중'으로 명확히 정의하고 불명 수/비율을 요약·일별 표에 함께 보여주거나, 불명 입력을 고려한 null/부분확인 표시 계약을 정한다. 어떤 선택이든 모두 False와 모두 None이 화면에서 같아서는 안 된다. 기존 unknown/보고서 검사에 모두 None 및 True/False/None 혼합 입력을 추가하면 된다.

### D2 — 새 BR 형식 원본의 범위 축소가 옛 날짜를 조용히 활성 상태로 남김

- 심각도: **중간(P2)**. 재현 상태: **격리 SQLite와 합성 입력으로 직접 재현**.
- 위치: `src/solarops/pipeline.py:254`–`:260` 및 해당 조건 내 publish 경로. 새 bounds 밖의 날짜는 처리하지 않고, 기존 expected active에 대한 철회/거부 분기가 없다.
- 최소 입력: 같은 요청 `[2024-04-01, 2024-04-03)`에 v1은 1·2일 각 1000W 한 행, v2는 1일 한 행만 제공. v2는 오류 없이 partitions=1로 끝난다. 조회에는 `04-01/v2/0.25kWh`와 `04-02/v1/0.25kWh`가 함께 남는다.
- 영향: 새 스냅샷에서 날짜를 제거한 정정으로 재처리하려는 경우, 요청 범위 내 과거 에너지가 현재 결과에 남는다. 계보는 남아 있으므로 추적은 가능하나 사용자가 성공 결과만 보고 정정이 완료됐다고 오해할 수 있다. 요청 범위 밖 날짜를 보존하는 기존 targeted replay의 의도와는 다른 경우다.
- 범위 주의: BR-PVGen은 현재 고정 배포 원본이며 실제 원천 철회를 관찰했다는 주장은 아니다. 기존 CLI가 새 source_version의 변경 입력을 허용하는 경계에 대한 발견이다. ONS의 철회 처리는 이 문제가 없으며 선택 검사도 통과했다.
- 최소 개선: BR 입력의 snapshot/patch 의미를 명시한다. 이 형태의 정정을 지원하지 않는다면 요청 범위 안 기존 active가 새 bounds에서 빠질 때 명시적으로 거부하고 안내한다. 지원한다면 명시적 철회 manifest 또는 활성 전환 정책을 CAS·계보와 함께 구현한다. 원본·과거 보고서 삭제는 필요 없다. 기존 변경 입력/targeted replay 검사에 한 사례를 확장한다.

## 강점과 남는 제한

가장 좋은 부분은 정상 경로만 시연하지 않는다는 점이다. 실패 중간의 이전 게시 보존, 여러 날짜 중 일부 완료, 오래된 작업의 역순 완료, raw 캡처 중 입력 변경, 버전 충돌, artifact 손상을 각각 다른 경계로 다룬다. ONS에서는 단위와 시각을 추측해 기존 발전량에 합치지 않은 선택도 적절하다.

MinIO source archive/base image digest 고정, BR 오류 코드 허용 목록, 조회량 제한은 후속 개선 가치가 있다. 다만 이번에 공급망 침해·비밀 유출·실제 조회 성능 장애를 재현한 것은 아니므로 확인된 사고나 높은 심각도 결함으로 보고하지 않는다. 외부 인증·HA·운영 SLO를 추가해야 점수를 얻는다는 뜻도 아니다.
