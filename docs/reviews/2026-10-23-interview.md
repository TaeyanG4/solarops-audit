**두 모델 모두 신입·주니어 데이터 엔지니어 면접 초대를 권고했고, 중급 역량은 이 저장소만으로 판단하기 어렵다고 평가했습니다.** 데이터 의미·계보·실패 게시 방어는 강점이며, 본인이 설계를 설명하고 작은 변경을 구현할 수 있는지는 실제 면접에서 확인해야 합니다.

## 독립성·실행 범위

- 같은 기준 코드와 평가 항목을 주고 상대방의 결과를 전달하지 않았습니다. Astra는 새 대화 이력의 에이전트, Fable은 Claude Code의 새 비대화형 세션입니다. 이전 기술 검토 문서는 과거 근거로 읽을 수 있었지만 이번 상대 평가를 읽지는 않았습니다.
- Fable 요청 별칭은 `fable`, 실제 init 및 응답 모델은 `claude-fable-5-1`, 세션은 `2c9f8b53-0a1e-4630-a410-8a9ee5e83efb`입니다. Read/Glob/Grep만 허용했고 93회 도구 호출 후 정상 종료했습니다. 테스트·브라우저·서비스 확인은 실행하지 않았습니다.
- Astra는 핵심 코드·문서·테스트를 읽고 기존 계약 함수 3개를 메모리에서 직접 실행했습니다. 에너지/누락/동일 중복, UTC offset, DST 검사가 통과했습니다. pytest 전체 실행이나 실제 인프라 재검증은 아닙니다.
- 본 세션은 아래 세 경계를 **격리 합성 CSV·SQLite·로컬 파일**로 재현했습니다. 공개 데이터·실행 서비스·스케줄·앱 코드를 변경하지 않았습니다. 상시 테스트나 검증 스크립트도 추가하지 않았습니다.
- 모델·점수·재현 결과는 [기계 판독 근거](2026-10-23-interview-evidence.json), 실행 명령과 보존 위치는 [작업 기록](../worklog/2026-10-23-interview.md)에 있습니다.

## 공통 강점과 면접 위험

두 모델 모두 다음 구현을 강점으로 확인했습니다.

1. **서로 다른 데이터 의미를 보존합니다.** BR-PVGen의 추정 kWh, 원본 보간·표본 수, 무효·누락·유효한 0을 구분합니다. ONS의 MWmed와 미명시 시간대를 억지로 기존 에너지에 합치지 않습니다.
2. **실패와 동시 실행의 게시 경계를 구현했습니다.** 불변 객체를 먼저 저장하고 검증 후 DB의 활성 포인터를 전환합니다. 기대 run ID 비교, 이전 성공 보존, ONS 월별 cursor·manifest 트랜잭션이 코드와 테스트에 있습니다.
3. **도구 역할과 측정 한계를 설명합니다.** 공통 CLI, Airflow 일정·재시도, KPO 작업 격리, 독립 저장소를 구분합니다. 공개/합성·단일 호스트·일회 측정의 한계를 명시합니다.

가장 큰 면접 위험은 본인 이해도의 미확인입니다. AI 사용과 짧은 개발 기간은 개인 역량 부족의 증거가 아닙니다. 다만 저장소만으로 개인의 SQL·Python·운영 판단 능력을 입증할 수도 없습니다. 본인이 선택·거절한 설계, 재현한 실패, 수정한 경계를 실제 코드로 설명하는 확인이 필요합니다. 문서량과 숫자 나열도 외부 독자의 탐색 부담으로 지적됐습니다.

## 코드 재확인과 합성 재현

### 1. 시간대 없는 구간 밖 행이 품질 분모에 들어감 — 재현됨

Fable은 [source_bounds](../../src/solarops/pipeline.py)의 DuckDB `TRY_CAST`와 [normalize](../../src/solarops/normalize/parquet.py)의 timezone 필수 검사가 다르다고 지적했습니다. 본 세션은 실제 `ingest`를 다음 합성 인버터 자료로 실행했습니다.

- 동일 인버터의 `2024-03-31T23:45:00`(시간대 없음), `2024-04-01T12:00:00Z`, `2024-04-01T12:15:00Z`. 요청은 4월 1일 하루입니다.
- 첫 행을 직접 정규화하면 `TIMESTAMP_TIMEZONE_MISSING`으로 거부합니다. 그러나 기간 밖이라 정규화 대상에서 빠지면서 전체 범위 계산에는 UTC로 들어갑니다.
- 실제 게시 결과는 **기대 50 / 관측 2 / 누락 48 / 관측률 4%**였습니다. 시간대 없는 행을 제외한 대조 입력은 **기대 2 / 관측 2 / 누락 0 / 관측률 100%**였습니다.

따라서 단순 스타일 불일치보다 영향이 큽니다. 잘못된 입력은 명시적으로 실패해야 하며, 범위 계산에 기여하는 전체 행에 같은 시각 계약을 적용해야 합니다. **현재 공개 원본에서 이 조건이 발생했거나 기존 보고서가 잘못됐다고 확인한 것은 아닙니다.** INT-01로 우선 수정 계획에 등록했습니다.

### 2. 관측 없는 보고서의 보간율을 0%로 표시 — 재현됨

Fable은 [render.py](../../src/solarops/reports/render.py)의 분모 0 분기와 읽기 모델의 `None` 처리가 다름을 지적하면서 실제 영향은 없을 수 있다고 평가했습니다. 본 세션은 도달 가능한 **관측 수 0** 경계로 확인했습니다.

- 원본 유효 시각이 3월 31일 23:45Z와 5월 1일 00:00Z인 합성 입력에서 4월 1일을 게시했습니다. 원본 범위 안의 전체 누락일이므로 정상적으로 파티션을 유지합니다.
- 일별 지표는 **기대 96 / 관측 0 / 보간율 null**, overview도 보간율 `null`이었습니다.
- 실제 `build_report`의 manifest는 **interpolation=0**, HTML은 0.00%로 표시하는 분기를 탑니다.

기대 슬롯 분모가 0인 파티션의 도달성까지 주장하지 않습니다. **관측 분모가 0인 보간율에서 의미가 달라지는 결함**은 재현됐습니다. INT-02에서 새 보고서의 unknown 표시를 정렬하되 과거 발행물은 보존해야 합니다.

### 3. ONS 실패 원인이 ValueError로 합쳐짐 — 재현됨

두 모델이 공통 지적한 [sync_month](../../src/solarops/acquisition/ons.py)의 `error_code=type(exc).__name__`를 확인했습니다. 다운로드는 합성 응답으로 대체하고 publish 경계에 `ONS_SOURCE_CONTRACT_CHANGED`, `ONS_SCHEMA_CHANGED`를 각각 주입했습니다. 두 실행 모두 실패 기록의 코드가 **ValueError**였습니다. 실제 HTTP 장애를 재현한 것은 아닙니다.

이 문제는 진단 정보 손실입니다. Fable의 “메시지 접두사 한 줄 변경”을 그대로 채택하지 않고, 알려진 도메인 오류의 허용된 코드와 알 수 없는 예외 fallback을 사용하는 INT-03을 계획했습니다. 임의 예외 메시지에 경로·접속 문자열 등이 섞여 노출되지 않도록 해야 합니다.

## 과장하거나 그대로 수용하지 않은 의견

| 평가 의견 | 본 세션 판단 |
|---|---|
| Astra: 원본 측정은 artifacts에 있어 외부 검증이 제한됨 | 맞지만 [기존 benchmark JSON](../benchmarks/incremental-v0.5.0.json)에 run ID·시각·자원·DB/S3 증감·hash 요약은 이미 커밋돼 있습니다. 공유 증거가 전혀 없다는 뜻은 아닙니다. |
| Fable: S3 신규 바이트가 CSV 반복 스캔 비용을 보여줌 | 반복 파일 읽기 경로는 코드에 있습니다. 그러나 S3 신규 바이트는 저장된 객체량이며 읽기 횟수·디스크 I/O 비용의 직접 측정이 아닙니다. |
| Fable: `round(ratio × observed)` 복원이 손실 있는 근사 | 보간 건수를 직접 저장하는 설계와의 비교 질문은 유효하지만 현재 정밀도에서 실제 잘못된 건수는 재현하지 않았습니다. 확인된 결함으로 등록하지 않습니다. |
| Fable: ONS 충돌 날짜만 격리하는 방안 | 현재 월 단위 성공 snapshot 계약을 바꾸는 선택입니다. 상충한 자료를 임의 선택하지 않는 현 정책이 잘못됐다는 증거는 없습니다. |
| Fable: UTC 보고서와 localhost 링크 | 기본 UTC는 설정에 명시되어 있고 시간대는 파티션 키·보고서에도 기록됩니다. 현지 운영일 지원은 선택 과제입니다. localhost는 로컬 시연 경로이며 외부 공개 데모로 소개하면 안 됩니다. |
| 두 모델: 중급·장기 운영 근거 부족 | 스키마 이행, stale run 조정·경보, 보존 정책, 교차 호스트 복구·SLO는 운영 범위가 확대될 때 검증합니다. 기술 이름 추가로 대체하지 않습니다. |

## 후속 우선순위와 면접 준비

새로 확인한 세 항목만 [plan](../../plan.md)에 등록했습니다. 기존 PORT-01~04 완료 기록은 보존하며, 이번 결함 발견으로 “현재 미완료 기술 항목 없음” 상태는 갱신합니다. 평가는 완료했지만 수정은 아직 실행하지 않았습니다.

| 순서 | 작업 | 점수 | 필요한 완료 근거 |
|---|---|---:|---|
| 1 | INT-01 범위 계산과 정규화의 시각 검증 통일 | 21 | 구간 밖 timezone 누락/그리드 오류도 명확히 거부, 실패 게시 보존, 정상 입력 hash 유지 |
| 2 | INT-02 관측 없는 보고서의 보간율 unknown 유지 | 19 | 일별·overview·새 manifest/HTML의 의미 일치, 실제 0%와 구분, 과거 보고서 보존 |
| 3 | INT-03 안전한 ONS 오류 코드 보존 | 16 | 계약/파싱/충돌 구분과 비민감 fallback, 성공 cursor 보존 |

면접 준비에서는 코드 없이 먼저 설명한 뒤 함수·테스트로 근거를 보여주는 연습을 권합니다.

1. 객체 업로드 후 죽었을 때와 늦은 작업이 완료될 때, 활성 결과·고아 객체·재시도가 어떻게 달라지는지.
2. 추정 kWh, MWmed, UTC, 무효/누락/보간의 의미와 분모를 어떻게 정하는지.
3. 47.3% 단축으로 무엇을 말할 수 있고, 단일 CLI 기준·반복 순서 교차 측정으로 어떻게 보완할지.
4. Airflow의 일정·재시도와 KPO의 실행 역할, 상태가 running으로 남았을 때의 운영 판단.
5. 이번 세 결함 중 하나를 직접 설명하고 작은 패치와 관련 기존 테스트를 작성하는 방법.

새 회귀 검사나 외부 인프라 확대를 평가의 기본 요구로 추가하지 않습니다. 데이터 무결성·보고서 의미·진단 경계의 수정 시 관련 기존 테스트를 필요한 만큼 확장하는 것이 적절합니다.
