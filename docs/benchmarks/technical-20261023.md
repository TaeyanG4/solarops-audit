## 선택형 실제 서비스 CI

[첫 실행](https://github.com/TaeyanG4/solarops-audit/actions/runs/39895412331)은 `ed14dbb`의 기존 PostgreSQL·MinIO 검사 **5통과/6.15초**입니다. 트랜잭션 실패 후 이전 결과 보존, 재실행, 동시 버전 등록, 보고서 역순 완료·업로드/카탈로그 실패를 검사했습니다. 이 실행 이후 추가한 보고서 비교·정렬 인덱스의 최종 검증은 작업 기록에서 별도로 구분합니다.

GitHub hosted 무료 잔여량 조회는 토큰의 `user` scope 부족으로 실패해 권한 확대나 유료 실행 대신 로컬 실행을 택했습니다. runner2.338.1 다운로드 SHA-256은 `08e9ccb3604d2462c24b5e33604dc30810296ca15cc65f23cffd4317eb144c37`입니다. 실행기는 작업 후 등록 해제되고 이 작업의 컨테이너만 중지합니다. 초기 WSL 입력 개행 문제로 생긴 오프라인 등록도 해제했습니다.

## 보고서 비교 계약

- 결과는 `unchanged / changed / unavailable`입니다. 계산 버전 변경은 별도 이유를 반환합니다. 같은 입력 재처리도 실행 근거가 달라지므로 changed이며 수치 변경·고장 확정과 구별합니다. 오래된 보고서의 선택 범위 부재나 저장소 오류는 unavailable입니다.
- 조회 시점의 비교이며 `Cache-Control: no-store`를 적용합니다. 실시간 감시·자동 재발행 기능이 아닙니다. 과거 HTML/CSV/manifest는 변경하지 않습니다.
- 공개 PS_001 2024-04를 새 ID `a4fbf16f-a877-4ed0-b35a-e4f7f49ebda9`로 발행했습니다. 이전 ID `5fd1a0be-9514-4f39-ad76-06f80c157ec5`의 HTML/manifest와 공개 overview 응답은 바이트가 동일합니다.

## 별도 인스턴스 복원

`service_restore_drill.py --isolated-target`로 새 PostgreSQL16.10·MinIO 컨테이너, 무작위 자격증명, 컨테이너별 저장공간, 임의 loopback 포트를 사용했습니다. 각각 CPU1개·메모리768MiB로 제한했습니다. 원본 합성 DB/버킷은 기존 서비스에 별도로 만들었으며 실제 앱 DB/공개 객체는 수정하지 않았습니다.

초기 실행은 복원 입력 폴더 생성 누락으로 실패했습니다. 폴더를 명시적으로 생성하고 예외 시에도 자신이 만든 컨테이너를 중지하도록 수정했습니다. 실패 자료는 남겼습니다. 수정 후 객체 **27개**, 활성 파티션 **7개**, 원본 SHA·기존 보고서·API·raw 재처리 해시·원본 카탈로그/객체 비변경을 확인했습니다. 복원 시작부터 API 확인까지 **0.953초**, 전체 **6.891초**는 작은 합성 자료의 로컬 측정이며 운영 RTO/RPO가 아닙니다.

실행은 호스트 Python 소스이며 evidence의 worker0.4.1 image ID는 기존 스크립트가 기록한 참고 이미지입니다. 실제 복원 서버는 기록된 PostgreSQL·MinIO 이미지입니다. 같은 물리 호스트이므로 호스트/디스크 장애와 외부 백업 저장소의 재해복구를 검증한 것은 아닙니다.

## 동시 실행 이력 조회

합성 JSON 실행 이력25,000/100,000건, 100개 발전소 ID, 800자 padding, partition90%/batch10%를 새 PostgreSQL에 적재했습니다. 실제 발전소 관측이나 처리 완료 실적으로 사용하지 않습니다. API/DB는 각각 CPU1개·메모리768MiB의 별도 컨테이너입니다. 기존 앱 DB에는 부하를 보내지 않았습니다.

각 조건은 고정 동시 요청1/4/8개, 워밍업2회 후40회 요청, 20행 응답입니다. 첫 페이지·offset10,000·발전소 필터를 측정했습니다. 측정 전 조사 기준은 **동시 요청4개에서 p95>1,500ms 또는 요청 오류 발생**으로 정했습니다. p95는40개 표본의38번째 값이며 외부 운영 SLO가 아닙니다.

100,000건의 전체 조회는 JSON 시각 정렬을 위한 순차 스캔·디스크 외부 정렬이 병목이었습니다. 조직·정렬 시각·run_id의 PostgreSQL 표현식 인덱스 `ix_pipeline_run_org_updated` 하나를 추가했습니다. API 정렬·페이지·응답 계약과 SQLite는 유지합니다. 조회용 Catalog는 DDL을 실행하지 않습니다.
